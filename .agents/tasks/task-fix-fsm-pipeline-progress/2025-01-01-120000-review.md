# Pipeline progress as forward-only high-water-mark

The FSM pipeline display previously showed `job.status` — the *current* FSM state — which regresses when the orchestrator loops back to earlier phases for additional vulnerabilities. This change introduces a separate `pipeline_phase` field that only moves forward, giving the UI a monotonically advancing progress indicator regardless of per-iteration state transitions.

The approach is minimal: a class-level `FSM_ORDER` list provides positional comparison, `_maybe_advance_state` updates the high-water-mark on every tool dispatch, `_advance_to_complete` forces it to COMPLETE, and the column round-trips through the DB via `hydrate_state`/`save_state`. The template falls back to `job.status` when `pipeline_phase` is null, preserving backward compatibility for existing rows.

**Watch for:** The `pipeline_phase` column is nullable with a default but there is no migration for existing databases (confirmed). `_advance_to_complete` unconditionally sets `pipeline_phase = COMPLETE` without checking the current high-water-mark, creating an asymmetry with `_maybe_advance_state`'s guarded logic (confirmed, though functionally harmless since COMPLETE is always the highest state).

## High-level view

The high-water-mark lives entirely in `_maybe_advance_state`: when the target state's index in `FSM_ORDER` exceeds the current `pipeline_phase` index, the field advances. This is the only non-terminal write path, and it means the phase tracks tool activity rather than explicit FSM transitions — a deliberate choice that decouples the progress display from the internal transition graph.

Persistence adds a nullable `pipeline_phase` column to `AnalysisJob` and wires it through `hydrate_state`/`save_state`. The nullable-with-default pattern avoids blocking schema changes but means existing databases using `create_all` get the column on next restart while production databases using a migration tool would need an explicit ALTER TABLE.

Test coverage targets the three key behaviors: non-regression, persistence round-trip, and `_advance_to_complete` setting COMPLETE. The gap is that no test exercises `hydrate_state` with a null `pipeline_phase` column — the backward-compatibility fallback path.

## High-water-mark semantics and `FSM_ORDER` drift risk

The use of `.index()` on `FSM_ORDER` means an unrecognized state would raise `ValueError` at runtime rather than failing gracefully. Today all callers pass states that exist in `FSM_ORDER`, but `FSM_ORDER` must stay in sync with any new states added to `FSMState` and `TRANSITIONS`. Since `FSM_ORDER` is a manually maintained list duplicating knowledge already encoded in the `TRANSITIONS` dict's topological order, adding a state to one but not the other would silently produce incorrect high-water-mark comparisons or crash on `.index()`.

The explicit `self.pipeline_phase = FSMState.COMPLETE` in `_advance_to_complete` bypasses the guarded comparison. If a post-COMPLETE state were ever added (e.g., ARCHIVED), the unguarded assignment would need updating — whereas `_maybe_advance_state` would handle it correctly by construction.

## Schema deployment gap

```python
pipeline_phase = Column(String(50), nullable=True, default="ready")
```

The `default="ready"` is a Python-side default only. SQLAlchemy `create_all` is a no-op for tables that already exist — it won't ALTER existing tables to add the column. Any deployment that doesn't drop-and-recreate the database will have rows with NULL `pipeline_phase` permanently unless manually patched. The `hydrate_state` fallback handles this gracefully at runtime, but the deployment step is undocumented.

## Test coverage gap

What's not tested:

- **Null `pipeline_phase` in DB**: a job created without `pipeline_phase` set (simulating a pre-existing row) followed by `hydrate_state` — verifying the fallback to `self.state`.
- **Invalid `pipeline_phase` string**: the `except ValueError` branch in `hydrate_state` that falls back when the stored value isn't a valid `FSMState` member.

Both are the exact paths that would break silently if the fallback logic were accidentally removed.
